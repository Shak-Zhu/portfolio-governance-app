## 本次返工原因（P0，必须完整修复）

WP-008 的现有测试通过，但独立代码审计发现以下问题，不能进入生产：

1. `POST /api/backups/restore` 接受请求体 `targetDbBinding`，再用 `(c.env as Record<string, unknown>)[targetBinding]` 取数据库。登录用户可传入 `DB`；`String(targetDb)` 不是可靠的生产数据库身份校验，因此存在恢复覆盖生产 D1 的路径。
2. 生产 `wrangler.toml` 只有 `DB`，没有隔离 D1 binding；网页固定发送 `TEST_DB`，生产环境会返回 400，恢复演练并不能真实完成。
3. `purgeOldBackups()` 没有覆盖 31 份对象的真实保留测试；不得以未执行删除操作的 G3/G4 代替。
4. `restoreBackup()` 只遍历备份里的对象，不强制完整六表集合；损坏或缺表备份可能绕过完整性校验。

## scope_in

### A. 彻底封死生产恢复路径

1. 移除请求体 `targetDbBinding`，客户端不可指定任何 D1 binding、数据库名称、SQL 或 R2 bucket。
2. `POST /api/backups/restore` 的唯一允许目标必须是代码中显式固定的 `env.RESTORE_DRILL_DB`；不得由字符串索引 `env`。
3. `Env` 中将该 binding 声明为 `RESTORE_DRILL_DB?: D1Database`。如果绑定不存在，接口返回明确 503（如“恢复演练隔离库尚未由管理员配置”），不得退化为 `DB`，不得尝试恢复。
4. `wrangler.toml` 只新增/保留 binding 名称与 Codex 配置占位说明；**不得伪造 database_id、不得创建 D1、不得部署**。Codex 会在 PM/QC 通过后创建隔离 D1、写入真实 ID 并发布。
5. 恢复函数的参数/调用契约必须使其无法在生产 HTTP 路径收到 `env.DB`。禁止使用 `String(targetDb)`、数据库名称字符串匹配等推断型保护作为唯一或主要防线。
6. UI 不再向接口发送 `targetDbBinding`；只有当服务端返回可演练状态时才启用演练按钮。隔离库未配置时显示明确的“等待管理员配置隔离恢复库”，不伪报可执行。

### B. 强化备份与恢复完整性

1. 备份和恢复严格要求且只允许以下六张表，缺一不可、不可多表：
   `portfolios`、`projects`、`stages`、`steps`、`project_links`、`audit_events`。
2. 恢复前验证：`schemaVersion`、完整六表集合、每表数组/行数/SHA-256、整体 `contentSha256`。任一失败时，**在对隔离库执行任何 DELETE/INSERT 前**拒绝。
3. 对有效备份恢复后，逐表从隔离 D1 回读，验证行数与表 SHA-256；失败即抛错。不得仅返回输入 manifest 的摘要即声称恢复通过。
4. R2 保留策略新增真实测试：创建至少 31 个可排序的备份对象，执行清理后断言只剩 30 个，删除的是最旧 key，最新 30 个完整保留。
5. 如果 R2 `delete()` 的实际返回类型为 `void`，不得把 `undefined` 当作删除失败；删除抛错必须向上传播，成功删除后通过重新 list 或测试桩证明对象确已移除。
6. `scheduled()` 与手动备份继续复用同一备份服务；新增测试至少直接调用 scheduled handler 或 `runScheduledBackup()`，断言它会写入 R2 并执行保留策略。

### C. 真实、非破坏性 E2E

1. E2E/集成环境必须绑定两个不同的 D1：生产模拟库 `DB` 与隔离恢复库 `RESTORE_DRILL_DB`。
2. 真实流程：登录 → 创建备份 → 调用恢复演练 → 隔离库六表回读并验证；同时在 `DB` 预置哨兵数据，恢复后断言哨兵未被清空/覆盖。
3. 负向测试：传 `{ "targetDbBinding": "DB" }` 或任意附加字段不会改变目标，接口要么忽略该字段要么以 400 拒绝，且 `DB` 哨兵仍在。
4. 无会话访问所有备份 API 仍为 401；MCP tools/list 仍为原 31 个工具，不能出现 R2/恢复/任意 SQL 工具。

## 验收标准

1. 生产 HTTP 路径中不存在动态 `targetDbBinding` / `env[用户输入]` 选择 D1 的逻辑；恢复唯一显式目标是 `RESTORE_DRILL_DB`，未绑定时为 503，永不回退至 `DB`。
2. E2E 以两个不同 D1 binding 执行真正恢复；隔离库逐表内容与备份一致，`DB` 哨兵数据仍在。
3. 损坏的 SHA、缺失任一业务表、出现未知表的备份都会在写入隔离库前被拒绝。
4. 31 份 R2 备份的保留测试证明最终精确保留最新 30 份；模拟删除异常会被调用方识别为失败。
5. scheduled 路径与手动备份均有可执行测试证据，而非字符串断言。
6. `npm run lint`、`npm test`、`npm run test:e2e`、`npm run build`、`git diff --check` 全部通过；最终报告给出实际命令输出和 Read Evidence。
7. `RESULT.md` 使用中文，并列明未执行的生产动作。最终状态只能为 `implemented, pending PM/QC review`。
