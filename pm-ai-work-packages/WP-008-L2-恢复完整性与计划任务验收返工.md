## scope_in

### A. 严格备份 manifest 合同

1. `validateBackupManifest()` 必须分别精确比较：
   - `Object.keys(manifest.tables)`；
   - `Object.keys(manifest.tableSummaries)`；
   两者都必须与固定六表集合完全一致。未知、缺失、重复（对象无法重复但应说明）、summary/table 不一致都必须拒绝。
2. 要求 `schemaVersion` 等于当前受支持版本；不能只判断非空。
3. 对所有拒绝路径新增可执行测试：
   - 缺一张 `tables` 表；
   - `tables` 多出未知表；
   - `tableSummaries` 与 `tables` 集合不一致；
   - 逐表 SHA 不一致；
   - contentSha256 不一致。
4. 每个负向测试都要在隔离 D1 预置哨兵数据后运行，并断言验证失败时隔离库没有发生 DELETE/INSERT。

### B. 恢复后内容级验证

1. G8 必须从 R2 读取当次 manifest，逐表计算/比对：
   - 恢复库行数 == manifest rows；
   - 恢复库表 SHA-256 == manifest tableSummaries[table].sha256。
2. 为避免无排序 SQL 的不稳定哈希，备份读取与恢复后验证必须使用同一个确定性排序策略（例如所有六表 `ORDER BY rowid ASC`）；测试也使用相同口径。

### C. scheduled() 真正执行

1. E2E 不能再以手动 `/api/backups` 代替 scheduled。
2. 直接从 Miniflare Worker / module 调用 `scheduled()` 或使用平台提供的 dispatchScheduled 方法，执行实际 cron handler。
3. 断言 scheduled 前后 R2 对象数量增加，新增对象含六表摘要和 SHA-256；同时确认保留策略仍不超过 30。
4. 保留手动 API 测试，但单独命名；不得将其称为 scheduled 测试。

### D. 隔离库就绪状态与 UI

1. 新增只返回布尔能力状态的、登录保护的 API，例如 `GET /api/backups/status` → `{ restoreDrillAvailable: boolean }`。不得泄漏 D1 ID、数据库名称、secret 或 R2 内容。
2. `loadBackups()` 或进入备份标签页时读取该状态：
   - `false`：恢复演练按钮禁用，显示“等待管理员配置隔离恢复库”；
   - `true`：允许选择备份并执行演练。
3. 未登录访问该状态 API 必须 401。
4. 不增加 MCP 工具，不接受任何客户端数据库/binding 参数。
